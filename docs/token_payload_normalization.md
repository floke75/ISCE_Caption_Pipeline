# Token Payload Normalization

The token normalization helper introduced in this update ensures that every
subsystem works with the same, predictable representation of token metadata.
The sections below summarise when the helper is invoked, the guarantees it
provides, and how to extend it safely.

## Why normalization lives in `isce.token_utils`

Token payloads originate from a number of sources: JSON exports generated by the
alignment scripts, cached dataclass instances used by the scorer, and bespoke
objects created inside tests. Previously each subsystem performed its own
ad-hoc conversions, which made the behaviour difficult to reason about. The
`normalize_token_payload` helper centralises this work by:

- Deep copying the original object so downstream code never mutates shared
  structures by accident.
- Coercing mixed numeric types (for example, string `"7"` or float `7.0`) into
  the integers and floats expected by guardrail features.
- Normalising boolean guard flags (`speaker_change`, `line_break_after`, and so
  on) so truthiness checks remain deterministic.
- Preserving or backfilling the `token_index` so dependency-aware features stay
  aligned across lookahead and refinement passes.

## Where the helper is used

The helper is now imported by every component that needs stable token data:

- **Beam search (`isce.beam_search`)** – converts raw tokens into the
  dictionaries consumed by the scorer, including lookahead slices and bigram
  contexts.
- **Model builder (`isce.model_builder`)** – ensures training features derived
  from historical corpora use the same string keys that the live scorer expects.
- **Training CLI (`scripts/train_model.py`)** – normalises tokens before
  generating feature tables so iterative reweighting exercises the same data the
  scorer will ultimately see.

Tests under `tests/test_token_utils.py` capture the contract in executable form
and serve as the canonical examples of supported inputs.

## Extending the schema

When new token attributes are added elsewhere in the pipeline, remember to
update `normalize_token_payload` so the field is coerced appropriately. Follow
this checklist:

1. **Decide the canonical type.** Is the field numeric, textual, or boolean?
2. **Add coercion in `normalize_token_payload`.** Use the existing helper that
   matches the canonical type or add a new `_coerce_*` function when necessary.
3. **Update tests.** Extend `tests/test_token_utils.py` with examples covering
   both well-formed and messy inputs.
4. **Document the behaviour.** Append a short note to this file or the relevant
   module docstring describing the new field and its expected shape.

Keeping the documentation and tests in lock-step with the helper makes the
normalisation pipeline easy to audit and evolve.
